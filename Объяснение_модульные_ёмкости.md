# Подробное объяснение кода: Модульные ёмкости и маршрутизация

Файл разбирает ноутбук `Модульные ёмкости.ipynb` (задание 3 из main.pdf): **зачем** написан каждый фрагмент, **какая математическая идея** за ним стоит и **как** для этого используется Pyomo.

Рядом лежат конспекты по ЛП, ЦЛП и транспортным задачам. Здесь акцент на формулировке **«адрес назначения — канал»** и смешанно-целочисленной модели модульных ёмкостей.

---

## 0. Общая схема

Каркас тот же, что в других ноутбуках:

1. `pyo.ConcreteModel()`
2. `Set` / `Param` / `Var` / `Constraint` / `Objective`
3. `SolverFactory("appsi_highs").solve(...)`
4. `pyo.value(...)`

Отличие задачи:

| Объект | Смысл |
|--------|--------|
| \(a_e \in \mathbb{Z}_{\ge 0}\) | сколько модулей ёмкости поставить на канале \(e\) |
| \(x_{te} \ge 0\) | сколько трафика **к назначению** \(t\) идёт по каналу \(e\) |
| \(C\) | размер одного модуля |
| \(d_e\) | длина канала (км) для второго критерия |

Это **MILP**: цель и ограничения линейны, но \(a_e\) целые. Непрерывная релаксация даёт нижнюю оценку, а не план установки оборудования.

### Специфика Pyomo здесь

**`Var(m.N, m.E, ...)`** — переменная с индексами «назначение + канал». В коде это `m.x[t, u, v]`, где `(u, v)` — ребро.

**`Param(..., default=0)`** для матрицы \(h\) — незаданные пары (источник, назначение) считаются нулевым спросом, не нужно заполнять весь квадрат \(|N|\times|N|\).

**`Expression`** для `module_count` / `distance_cost` / `total_flow` — именованные линейные выражения, которые можно подставлять в цель или ограничения без дублирования формулы.

**`clone()` + `fix()` + смена `Objective`** — лексикография и очистка циркуляции без пересборки модели с нуля.

## 1. Постановка (markdown ноутбука)

Два **отдельных** критерия из ТЗ:

\[
F_1 = \min \sum_e a_e, \qquad F_2 = \min \sum_e d_e a_e.
\]

Ограничение баланса — стандартное для destination-link: у источника \(n\neq t\) уходит \(h_{nt}\), в стоке \(t\) поглощается сумма всех требований к \(t\).

На канале суммарный поток по всем назначениям не больше \(C a_e\).

В ноутбуке явно разделено:

- что **обязательно по ТЗ** (два критерия, таблицы, визуализация, экспорт);
- что **добавлено** (лексикография \(F_1\to F_2\), удаление циклов в потоках).

## 3. Данные: directed и undirected

### Идея

В ТЗ редактор может создавать **ненаправленные** рёбра. В модели потоки направлены, поэтому undirected раскрывается в пару дуг \((u,v)\) и \((v,u)\) с **одной** длиной.

```python
def expand_links(d):
    links = dict(d.get('links', {}))
    for (u, v), length in d.get('undirected', {}).items():
        for a, b in ((u, v), (v, u)):
            links[(a, b)] = length
    return links
```

`normalize_data` возвращает копию только с `links`. `validate_data` проверяет узлы, \(C>0\), длины и достижимость спроса через `networkx.has_path` — это **ранняя диагностика**, окончательный `infeasible` всё равно ставит решатель.

Демо-сеть A–E в PDF числами не задана; как и в других ноутбуках курса, это учебный инстанс.

## 4. Модель `build_model`

### Множества и параметры

```python
m.N = pyo.Set(initialize=d['nodes'], ordered=True)
m.E = pyo.Set(initialize=list(d['links']), dimen=2, ordered=True)
m.h = pyo.Param(m.N, m.N, initialize=d['demands'], default=0)
```

`dimen=2` у `E` — каналы как пары. Тогда `m.a[u, v]` и `m.x[t, u, v]` читаются естественно.

### Переменные

```python
m.a = pyo.Var(m.E, domain=pyo.NonNegativeIntegers)          # или Reals при relax=True
m.x = pyo.Var(m.N, m.E, domain=pyo.NonNegativeReals)
```

Флаг `relax=True` меняет **только** домен \(a_e\): так получается LP-релаксация той же системы ограничений.

### Баланс

```python
def balance(m, t, n):
    rhs = m.h[n, t] if n != t else -sum(m.h[s, t] for s in m.N if s != t)
    return outflow - inflow == rhs
m.balance = pyo.Constraint(m.N, m.N, rule=balance)
```

Индексы `(t, n)`: для **каждого** назначения и **каждого** узла — своё уравнение сохранения. Это и есть формулировка «назначение–канал», а не «поток–путь» и не «commodity per demand».

`Constraint.Feasible` / `Infeasible` — на случай изолированного узла с нулевым/ненулевым балансом (пустая сумма в Pyomo недопустима).

### Ёмкость

```python
sum_t x[t, u, v] <= C * a[u, v]
```

На одном канале складываются потоки ко **всем** \(t\). Модули покупаются на канал, а не на назначение.

### Две цели через `mode`

```python
m.objective = pyo.Objective(
    expr=m.module_count if mode == 'modules' else m.distance_cost,
    sense=pyo.minimize,
)
```

ТЗ требует **два режима**, а не одну взвешенную сумму. Поэтому критерии решаются отдельно.

## 5. Решатель

```python
solver = pyo.SolverFactory('appsi_highs')
result = solver.solve(m, load_solutions=False)
...
m.solutions.load_from(result)  # только при optimal
```

Почему `load_solutions=False` и ручная загрузка: при `infeasible` не хотим читать «мусорные» значения переменных.

Сертификат: `status`, `objective`, `best_bound`, `relative_gap`. Допустимость \(\neq\) оптимальность: bound может быть ниже objective, пока gap не ноль.

Резервный SciPy-backend убран: для курса достаточно нативного `appsi_highs` (+ `highspy`).

## 6. Проверка, таблицы, циклы

`check_solution` проходит по всем `Var` и активным `Constraint` через `component_data_objects` — универсальная проверка после solve / после ручной подстановки значений.

`tables(m)` строит:

- загрузку каналов \(\sum_t x_{te} / (C a_e)\);
- ненулевые потоки \(x_{te}\).

`cycle_report`: для каждого \(t\) строится ориентированный граф рёбер с положительным \(x_{te}\); если есть цикл — маршрутизация **не строго корректна** в смысле §4.4.2 (трафик может крутиться).

## 7. Обязательный блок ТЗ: \(F_1\), \(F_2\) и LP

Цикл по `mode in ('modules', 'distance')`:

1. MILP → оптимум.
2. Та же модель с `relax=True` → нижняя оценка.
3. Проверка \(z_{LP} \le z_{MILP}\).

На демо-данных:

| Режим | MILP | LP |
|-------|------|-----|
| modules | 5 | 3.4 |
| distance | 22 | 16.8 |

В выводе строки помечены `scope: ТЗ: отдельный критерий`, чтобы не смешивать с лексикографией.

## 8. Добавлено: лексикография и очистка циркуляции

### Зачем

При \(\min\sum a_e\) длины не входят в цель. Среди всех решений с 5 модулями стоимость в модуль·км может быть 53, 45, … Лексикография:

1. Найти \(F_1^*\).
2. Добавить `module_count == F_1^*`.
3. Минимизировать `distance_cost`.

На демо: **45** модуль·км при 5 модулях.

Техника Pyomo:

```python
lex = models['modules'].clone()
lex.keep_modules = pyo.Constraint(expr=lex.module_count == optimal_modules)
change_objective(lex, lex.distance_cost)  # del_component + новый Objective
```

### Очистка циркуляции

```python
for e in m.E:
    m.a[e].fix(round(pyo.value(m.a[e])))
change_objective(m, m.total_flow)
solve_model(m)
```

Модули зафиксированы (`fix`) — топология ёмкостей не меняется. Минимизация суммарного потока выталкивает бесполезные циклы: балансы и ёмкости сохраняются, а \(x\) становится ацикличным (с учётом допуска).

Это **не** изменение исходной задачи ТЗ, а постобработка решения.

## 9. Доли пересылки \(f_{te}\)

Формула (4.19):

\[
f_{te} = \frac{x_{te}}{h_{a(e)t} + \sum_{e'\in\delta^-(a(e))} x_{te'}}.
\]

В коде для узла \(n\) и назначения \(t\):

```python
available = h[n, t] + sum(x[t, u, v] for входящие в n)
fraction = flow / available   # или NaN, если available ≈ 0
```

Если `available > 0`, сумма долей по исходящим должна быть 1 — assert в `forwarding_table`.  
Если знаменатель ноль, правило маршрутизации **не определено** текущей матрицей спроса (это прямо обсуждается в §4.4.1); ноутбук не «угадывает» кратчайший путь автоматически.

## 10. Визуализация

Два ряда:

1. **Модули:** толщина ребра \(\propto a_e\), подпись `flow/capacity (utilization %)`.
2. **Потоки по \(t\):** разные цвета назначений, толщина \(\propto x_{te}\), небольшой `connectionstyle` rad, чтобы параллельные потоки не сливались.

Три колонки: ТЗ-min modules / лексикография / ТЗ-min distance. Так видно, что «первый» оптимум по модулям и вторичный выбор — разные раскладки.

## 12. Тесты: что именно проверяется

| Тест | Смысл |
|------|--------|
| 12 единиц при \(C=5\) → 3 модуля | ceil-логика модульности |
| стоимость \(3\times 2\) | критерий \(F_2\) |
| агрегация A,B→M→T | потоки к одному \(t\) суммируются на канале |
| `undirected` → пара дуг, модули только «туда» | раскрытие неориентированного канала |
| нет пути → `infeasible` | статус решателя |
| \(C\le 0\) / NaN → `ValueError` | валидация входа |
| ручной цикл + `remove_circulation` | §4.4.2 |
| сумма \(f_{te}=1\) | инвариант таблицы пересылки |
| файлы экспорта существуют | отчётность |

## 13. Эксперименты

Меняется один фактор: \(C\) или множитель трафика. Смотрим, как растёт число модулей. Это чувствительность, а не новый критерий.

## Шпаргалка приёмов Pyomo в этом ноутбуке

| Приём | Зачем |
|-------|--------|
| `Set(dimen=2)` для каналов | индекс `(u, v)` |
| `Var(N, E)` | \(x_{te}\) |
| `NonNegativeIntegers` / релаксация в `Reals` | MILP vs LP-bound |
| `Param(..., default=0)` | разреженная матрица \(h\) |
| `Expression` | общие формулы цели |
| `Constraint(N, N, rule=balance)` | баланс для всех \((t,n)\) |
| `clone` + `fix` + новый `Objective` | лексикография / очистка |
| `component_data_objects` | универсальная проверка |
| `solutions.load_from` только при optimal | безопасное чтение |

## Как читать ноутбук

1. Выпишите модель: \(a_e\), \(x_{te}\), баланс, ёмкость, два критерия.  
2. В коде найдите каждый `Var`/`Constraint` — у него должна быть пара в формуле.  
3. Отделите блок «ТЗ» (§7) от «добавлено» (§8).  
4. Помните: числа 5 / 22 / 45 — для **демо-сети**; формулировка важнее цифр.  
5. Полный веб-редактор топологии в сдачу модели не входит — он был бы отдельным сервисом поверх тех же функций `build_model` / `run` / `export_solution`.
